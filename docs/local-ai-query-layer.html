Local AI Query Layer ​

Natural-language queries over locally available frontend data, powered by mobx-data.

Purpose ​

Let users ask questions like "show posts by julian" or "buscar posts sobre timeout" and get answers from the local identity map — no server round-trip, no data leaving the browser.

Architecture ​

User query (string)
  → LocalAiQueryService
    → LocalAiIntentParser (parse to structured intent)
    → LocalAiToolRegistry (dispatch to typed tool)
      → LocalAiTool (executes via mobx-data Store)
    → LocalAiResultFormatter (human-readable text)
  → LocalAiQueryResult

Key invariants ​

  • The parser never accesses IndexedDB directly.
  • The parser never inspects raw cache internals.
  • Only typed tools call mobx-data (via Store.peekAll, Store.peekRecord, etc.).
  • The parser outputs structured intents — it does not execute tools.

Supported intents ​

IntentDescriptionExample queries
get_posts_by_userPosts authored by a user"show posts by julian", "dame los posts de julian"
get_user_profileSingle user profile"get profile for julian", "perfil del usuario julian"
get_comments_by_postComments on a post"comments for post 123", "comentarios del post 123"
search_postsFull-text search on posts"search posts about timeout", "buscar posts sobre timeout"
get_recent_postsMost recent posts"recent posts", "últimos 5 posts"

Adding a new intent ​

  1. Add the intent name to LocalAiIntentName in LocalAiTypes.ts.
  2. Create an arguments interface (e.g. GetXArguments).
  3. Create a tool class implementing LocalAiTool<TArgs, TData> in tools/.
  4. Register the tool in your service setup.
  5. Add regex patterns to DeterministicLocalAiIntentParser (or let the model-backed parser handle it).
  6. Add tests.

Adding a new tool ​

Create a class implementing LocalAiTool:

typescript
import type { Store } from '@mobx-data/store';
import type { LocalAiTool, LocalAiQueryResult } from './LocalAiTypes.js';

export class MyNewTool implements LocalAiTool<MyArgs, MyData> {
  public readonly name = 'my_intent' as const;

  public async execute(arguments_: MyArgs, store: Store): Promise<LocalAiQueryResult<MyData>> {
    const records = store.peekAll('myModel').toArray();
    // ... filter / transform ...
    return { status: 'success', intent: this.name, data: records, message: '...' };
  }
}

Register it:

typescript
registry.register(new MyNewTool());

WebLLM parser (Qwen3.5-2B) ​

A fully implemented WebLlmIntentParser runs Qwen3.5-2B Instruct locally in the browser via WebLLM (WebGPU). No data leaves the browser.

Setup ​

bash
pnpm add @mlc-ai/web-llm

Usage ​

typescript
import { WebLlmIntentParser, LocalAiQueryService, LocalAiToolRegistry, LocalAiResultFormatter } from '@iamjulianacosta/mobx-data';

const parser = new WebLlmIntentParser({
  modelId: 'Qwen3.5-2B-q4f16_1-MLC',  // default
  onProgress: (report) => console.log(`${(report.progress * 100).toFixed(0)}% — ${report.text}`),
  temperature: 0.1,   // low for deterministic classification
  maxTokens: 128,
});

// Pre-load the model (optional — parse() auto-initializes)
await parser.initialize();

const service = new LocalAiQueryService(parser, registry, formatter, store);
const result = await service.query('dame los posts de julian');

How it works ​

  1. The engine downloads and caches the Qwen3.5-2B model (~1.2 GB) on first use.
  2. Each parse() call sends a system prompt with the intent schema + few-shot examples, plus the user query.
  3. JSON schema enforcement at the grammar level (via response_format.schema) guarantees the model always outputs valid structured JSON matching the intent schema.
  4. Qwen3 thinking mode is disabled (enable_thinking: false) to avoid thinking tokens in the output.
  5. The response is validated: unknown intents and "unsupported" return null.

Available model IDs ​

Model IDQuantizationSize
Qwen3.5-2B-q4f16_1-MLC4-bit float16 (default)~1.2 GB
Qwen3.5-2B-q4f32_1-MLC4-bit float32~1.2 GB

Lifecycle ​

typescript
// Check if loaded
parser.isLoaded; // boolean

// Explicitly unload the model to free WebGPU memory
await parser.dispose();

Requirements ​

  • A browser with WebGPU support (Chrome 113+, Edge 113+, Firefox Nightly)
  • @mlc-ai/web-llm installed (optional peer dependency)

When to use which parser ​

ParserProsCons
DeterministicLocalAiIntentParserInstant, zero dependencies, works in Node.jsOnly handles predefined regex patterns
WebLlmIntentParserHandles free-form queries, multilingual, extensible without code changes~1.2 GB model download, WebGPU required, slower first load
CascadeLocalAiIntentParserChains parsers: try each in order, fall back on null/errorCombines latency of multiple parsers

A common pattern is to cascade via CascadeLocalAiIntentParser: try the WebLLM parser first, fall back to the deterministic parser for unrecognized queries.

Custom parser interface ​

The LocalAiIntentParser interface is a single method:

typescript
interface LocalAiIntentParser {
  parse(query: string): Promise<LocalAiIntent | null>;
}

Other possible backends:

  • Chrome Prompt API — built-in browser model (Chrome 131+)
  • Transformers.js — classification pipeline in WASM/WebGPU
  • Remote LLM — if explicitly configured by the user

Testing strategy ​

Tests live in tests/ai/ and use Vitest.

  • Deterministic parser tests — verify regex patterns match EN/ES queries, edge cases (empty, unsupported).
  • WebLLM parser tests — mock @mlc-ai/web-llm, verify engine initialization, JSON parsing, error handling, Qwen3 config (enable_thinking: false, JSON schema enforcement).
  • Service tests — verify orchestration: empty → validation_error, unrecognized → unsupported, recognized → correct tool, tool throws → error.
  • Registry tests — verify registration, lookup, error wrapping.
  • Tool tests — mock mobx-data via buildStore + push, verify each tool against real identity-map data.

Run:

bash
npx vitest run tests/ai/
